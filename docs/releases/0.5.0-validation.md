## Common renderer milestone

Before production changes, compiled separate-render tests were RED: 16 failed
assertions because Cutter lacked separate physical ingestion and original-context
rendering. Log: `/tmp/livecut-v05-seam-red.log`.

The common renderer retains the original callback's beat accumulator through
output callback splits. Source origins use explicit render frames and classic
pitched retiming uses render-exclusive-end r+1. Rendering resets retain physical
history; duplicate input and out-of-order render frames report explicit errors.

Full engine suite GREEN: **158 cases / 4,295,971 assertions**. This includes all
four procedures, 50/75% Swing, 137/512-frame original contexts, 500 ms delayed
rendering, pitch/pan/fades/crusher/comb and a tempo change, plus the unchanged
immutable 0.3 Live oracle. The delayed comparison accumulates sample equality
and allocation checks without per-sample Catch assertions. Log:
`/tmp/livecut-v05-seam-all-engine.log`.

This milestone does not yet claim processor Studio mode, transforms, mode Apply,
UI, wrapped-host validation, or manual listening.

## Mode Apply / lifecycle checkpoint

RED2 cases /2 failing assertions established the missing coordinator and the
unprepared bypass gap: bypass passed .5 input despite the normal unprepared
path gating it. Both paths now gate unsupported/unprepared audio explicitly.
Log: `/tmp/livecut-v05-apply-red.log`.

Apply prebuilds only StreamResources off audio and outside the callback guard;
sample-rate preparation also prebuilds Hold/capture storage and installs it
under exclusion. CaptureService stays stable and retired storage/resources are
destroyed after our guard is released. Existing leases retain old storage.

One callback-guard-protected claim owns latency notification while its listeners
run off-guard. Nested/concurrent prepare/release leave pending work rather than
call another setter or wait. The owner reconciles the latest generation/rate,
bounded to two attempts per message turn, then retries on a later timer turn.
No claim is made about host-owned locks around host lifecycle calls.

Permanent tests use real JUCE processor listeners to synchronously prepare at
16kHz or release during setLatencySamples; a separate thread successfully takes
the callback guard in that listener. A measured impulse after reprepare lands
at8000 frames, matching the new16kHz resources. Eight concurrent preparations
racing eight Apply attempts cannot restore an obsolete candidate. Fresh audio
observations are invalidated on EVERY prepare and successful mode-resource
swap; release evidence cannot authorize a subsequent prepared configuration.
Healthy Live bypass observes running/stopped transport without advancing audio.

Additional RED13 assertions /2 cases exposed reused observation evidence and a
numeric-latency-only fast path that skipped final publication/resume after
bounded reentrant host churn. That fast path was removed: even an already
configured mode reconciles publication/suspension through the owner protocol.
Log: `/tmp/livecut-v05-observation-red.log`.

Focused GREEN: **70 processor/parameter/host-sync/capture cases /35,100
assertions**. Log: `/tmp/livecut-v05-apply-green.log`. Tests also restore saved
requested Studio before prepare and while existing Live audio plays, and restore
a0.4 state onto all four already-adjusted Recut controls. Requested, configured
and published active mode remain separate; UI latency uses an atomic published
snapshot. Four editor control-coverage assertions and unfinished transforms
remain outside this partial internal checkpoint's scope.
