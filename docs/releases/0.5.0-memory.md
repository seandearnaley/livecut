# Livecut 0.5.0 memory accounting

Measured against immutable production source
`c79fa634a17070ebfa3d4eb8888c47a5d7d8a0c1`, native ARM64 macOS, Apple Clang
21.0.0/libc++. A compile-only probe obtained actual type layouts. A separate
external executable used the actual StreamResources, WetHold and PhraseCapture
constructors and existing engine/JUCE objects, recording their `operator new`
byte requests at 48/96/192/384 kHz. All 20 constructor/snapshot trace rows matched
the source-derived categories exactly. No production source was changed, no
plug-in installed and no audio device or DAW opened by these probes.

The numbers below are prepared backing-storage byte requests, **not process RSS,
malloc size classes or a complete plug-in memory ceiling**. Live and Studio both
prepare the detector and all Hold/Capture buffers. Disabled effects still have
their prepared delay storage.

| Fixed Transform / optional Transform | 40 / 48 |

| LivePlayer / Cutter / StreamResources | 184 / 150008 / 150776 |
| Capture shared backing allocation | 192 (168-byte Storage +24-byte shared ownership block) |
| Full snapshot shared object allocation | 80 (in addition to its stereo PCM) |

StreamResources already contains Cutter, plans, candidate caches, Player and
timeline/detector object headers. Their individual fixed sizes must not be added
again. Dynamic Cut/PlayingCut vectors add 8192/20480 bytes. Snapshot metadata was
measured by constructing the same CapturedPhrase shared type with full channels;
worker-job/encoder storage is excluded.

For rate `sr`, Studio latency is `L=round(.5*sr)`, and Live uses `L=0`:

```text
raw stereo history frames = ceil(64*sr) + L + ceil(.020*sr) + ceil(.002*sr) + 2
timeline slots per ring   = L + 2
timeline ring bytes       = (L+2)*(352+16)
marker ring bytes         = 8192*32
Hold/Capture frames/slot  = C = min(ceil(64*sr), 12,288,000)
Hold PCM bytes            = 2*C*8
Capture PCM bytes         = 2*C*8
comb PCM bytes            = 2*(ceil(.050*sr)+2)*4
full export snapshot      = C*8 + 80 bytes
```

Actual constructor requests confirmed these capacities, including the timeline's
one-frame-callback worst case and all separately rounded source margins. At
48 kHz Studio, raw history has 3,097,058 stereo frames and each timeline ring has
24,002 slots. Hold/Capture each have two 3,072,000-frame stereo slots. Through
192 kHz their duration is 64 seconds; at 384 kHz it is 32 seconds. Raw history
remains a full 64 seconds plus the lead/margins above 192 kHz.

The subtotals include raw/comb PCM, Hold/Capture PCM, the complete StreamResources
allocation, Cut/PlayingCut vectors, marker/timeline rings and Capture shared
backing metadata. They exclude the processor-owned Hold/Capture wrapper objects,
processor/editor/APVTS/host objects and their dynamic storage, worker stacks/jobs,
file encoder buffers, allocator headers/rounding and VM/residency effects. The
two tiny wrapper objects alone are 144/104 bytes; they live within the excluded
processor/service, rather than being separate prepared allocations.

## Export and preparation overlap

The following are **source-order inventory calculations** using the verified
allocation requests, not measurements of concurrent RSS peaks. They assume one
operation at a time, equal old/new sample rates, no surviving old Capture leases
and no export snapshots unless explicitly included.

| Scenario | 48 kHz | 96 kHz | 192 kHz |
| --- | ---: | ---: | ---: |
| One full export snapshot, additional | 24.576 MB | 49.152 MB | 98.304 MB |
| Two overlapping full snapshots, additional | 49.152 MB | 98.304 MB | 196.608 MB |
| Studio steady +two full snapshots | 181.526 MB | 362.610 MB | 724.777 MB |
| New Studio stream during mode prebuild, additional | 34.070 MB | 67.698 MB | 134.953 MB |
| One Live↔Studio mode prebuild, combined | 157.420 MB | 313.956 MB | 627.026 MB |
| One sequential Studio host reprepare, combined | 230.678 MB | 460.914 MB | 921.385 MB |

Mode Apply builds only a new StreamResources while the previous stream remains
alive. Hold/Capture storage is reused. Its combined inventory is
`oldStream + newStream + HoldPCM + CaptureBacking`. The old stream is destroyed
after the swap and outside the coordinator's guard, before latency notification.

Full `prepareToPlay` moves out and destroys the old stream before prebuilding.
The old Hold and Capture backing remain while the new stream, Hold and Capture
are allocated. Without leases/concurrency, the same-rate Studio inventory is
`newStream + 2*HoldPCM + 2*CaptureBacking`. For a rate/mode change use each old/new
rate's actual categories, and take the maximum of the original steady inventory
and `newStream + newHold + newCapture + oldHold + oldCapture`.

Export replacement may retain both old and new snapshot PCM. A retired Capture
Storage can additionally survive through its leases: each distinct retained
generation adds its own two-slot Capture backing, deduplicated by ownership.
Concurrent preparation calls can each hold prebuilt stream/Hold/Capture storage;
there is no fixed number of such external calls encoded in this accounting.
Add their live inventories and any retired storage awaiting destruction, rather
than presenting the single-operation row as an unconditional ceiling. Snapshots
and leases can coexist with preparation, so their categories are additive.

These preparation probes do not establish callback allocation freedom or a hard
realtime claim; those belong to the separate callback regression tests. Windows
ABI and allocator/resident-memory measurements are not covered by this report.

Exact byte values, capacities, verified trace rows and source/library hashes are
in [the memory JSON](0.5.0-memory.json). The coordinating validation artifacts
retain external reproduction sources, compiler layouts, link command and raw
allocation traces. Earlier checkpoint estimates are superseded by this report.
